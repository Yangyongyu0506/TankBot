# TankBot 项目评估与开发建议

评估日期：2026-11-04。代码基线：`38207aa`（Navigation C3 航点闭环）。本报告是评估建议，不代表新增课程、物理参数或架构变更已经获得实施授权；不修改玩家代码与既有 Accepted ADR。

**总体判断：TankBot 已经形成可运行的机器人算法教学产品原型，下一阶段应同时加强实验反馈与工程验证，并沿现有 Navigation 闭环逐步扩展自主导航。** 当前不需要整体重写引擎或模块系统。

**评估方式与范围**

使用 Serena 的 Python 语言服务对 `host`、`runtime`、`sdk`、`protocol` 共 49 个 Python 模块建立符号索引，识别 238 个顶层符号，并追踪 Authority、关卡配置及工作区存储的引用关系。对调度、权限、输出提交、部署、计分、存储等关键符号读取实现。Serena 本次仅启用 Python 语言服务；Rust 物理、JavaScript 前端、构建/CI、关卡 YAML 与设计文档以源码检索和定向阅读补充。覆盖所有主要子系统，不声称逐行人工审计了所有源码、夹具和历史报告。

当前代码为公共入门 + Weapons C1–C5 + Navigation C0–C3，共十关。Navigation 已有双轮电压控制、理想里程计、带噪编码器/GPS EKF 和基于玩家估计的航点闭环。IMU 融合、连续路径跟踪、全局规划、局部避障与建图尚未实现。当前状态以 [文档索引](../README.md)、[路线图](../10_DEVELOPMENT_ROADMAP.md) 和对应领域规范为准。

**值得保留的基础**

1. **物理权威和玩家估计分离。** Rust Core 只接收经授权的执行器输入，玩家定位与目标估计通过 Authority 校验；ViewGateway 根据策略输出视图。Navigation C3 明确订阅玩家 EKF，没有用系统位姿补救错误估计。这是继续扩展教学任务时最重要的边界。
2. **两种 Runtime 共享语义。** 原生与浏览器使用同一 Python Authority、模块 Runner 和协议；物理来自同一 Rust Core。当前局部 Adapter 比复制一套 JS 游戏规则更容易保持一致。
3. **源码与部署有清楚的生命周期。** 工作区有文件锁、revision CAS、不可变快照、升级预览和旧版本保留；测试摘要绑定运行环境，部署在固定 tick 切换。Weapons/Navigation 工程隔离也已经落地。
4. **课程具有可复用的递进关系。** Weapons 从坐标变换推进到滤波、自瞄、装甲关联；Navigation 从轮控推进到定位、位置闭环。新关保留已学算法，避免每关重新搭建框架。
5. **声明式设计已有实用收益。** 关卡、权限、传感器、目标、规则和教材由 YAML 组合；进度前置构成图。已有临时插件、兼容冻结、失败/缺测/过期和源码保留回归，扩展基础较完整。

CI 的具体缺口是十个文件：`test_armor_ui.mjs`、`test_control_feedback.mjs`、`test_file_tree.mjs`、`test_level_tree.mjs`、`test_live_metrics.mjs`、`test_localization_view.mjs`、`test_map_preview.mjs`、`test_navigation_view.mjs`、`test_runtime_logs.mjs`、`test_workspace_dialog.mjs`。Python 测试中未发现调用这些 Node 文件的替代入口。这是已确认的自动化覆盖入口缺口，不是说这些组件没有测试。

运行时已有有界日志、批次往返统计、tick 统计及 `measure_m1*` 探针，因此应在现有诊断上增量扩展，避免重新搭一套监控系统。当前没有新的压力实验数据支持直接改预算、消息编码或 Authority 实现语言。

工作区已有不可变快照与原子 HEAD 更新，应保留这个恢复基础。后续存储清理必须把“可恢复”和“用户预览”作为验收项；不能为了减小体积破坏玩家历史。

**最值得先做的产品增量：小型算法实验台**

玩家已经会问“这个 KF/EKF 是否真正执行”“Q/R 怎么影响效果”“速度估计为什么滞后”“自瞄失败来自估计、提前量还是控制”。目前主要依靠累计 RMSE、日志和最后通关结果回答；这些反馈不足以快速定位具体失误。

第一版建议只提供：

- 在同一输入记录上比较两份保存版本，并提供测量/估计/协方差、创新、模块状态及关键采样/提交时刻。
- 显示累计误差与分段误差，明确数值单位、样本数、缺测区间和超时事件；滤波明显滞后时不必等到整局结束才发现。
- 保存一次失败的最小复现记录与代码 revision。给 UI 的真值对照继续依据显式授权，不能变成普通玩家 Python 的输入。
- 把“接口与短输入测试通过”和“闭环关卡评估”区分展示。当前 `test_batches=6` 只进行观察式短测，文档已经正确说明它不是完整闭环比赛。

**回放必须区分两类实验。** 对滤波器，同一组授权传感器样本可以公平比较版本；对控制器，输出会改变世界和后续观测，需要固定配置/初态重建闭环，不能把原传感器录制直接当作新控制器的真实闭环结果。最近航点验收也已指出：即使 seed 相同，部署时刻不同仍会消耗不同段的传感器随机流。已有 Navigation C2 的部分多 seed 验证值得保留，但还不能代替统一的跨关实验矩阵。

**建议的后续课程顺序**

| 阶段 | 新学习负担 | 可复用内容 | 开始前需明确的验收 |
| --- | --- | --- | --- |
| 连续路径跟踪 | 从“到达点并停住”进阶到沿路径连续运动 | 现有轮电压、EKF、Twist 参考和控制曲线 | 公开路径与速度参考；横向/航向误差、速度饱和、弯道稳定和终点停稳；先不增加新物理 |
| 已知地图全局规划 | 从航点输入进阶到自己产生可行路径 | 既有地图资产、位置控制与路径跟踪 | 给程序授权的地图 DTO、车体外形膨胀、安全间距、无解/重规划行为；用绕行地图评估 |
| 局部感知与避障 | 处理有限视野和动态/局部障碍 | 已有传感器实例调度、固定 tick、消息/配额验证 | 先确认测距/scan 的观测模型、遮挡、噪声、频率和消息预算，再开发课程 |
| 建图与定位扩展 | 从已知地图进阶到未知环境或更复杂融合 | 已验证的感知与规划闭环 | 分别设计 IMU 融合、地图表达、SLAM 目标；一次只引入一个主要难点 |

这条路线能把 Navigation C3 的成果连续用于更完整的自主任务。下一关具体路线、阈值、控制接口和新增物理/传感器参数仍需按项目惯例确认；本评估不替代确认。

Weapons 方向可在实验台稳定后安排机动跟踪、置信度驱动开火、多目标关联，但不必同时启动所有内容。现有 C5 还适合验证换板、连续缺测、相位展开和提前量的失败反馈；先提高可解释性，再增加目标数量。

**工程与课程建议如何穿插**

建议按“工程入口收口 → 实验台最小闭环 → 连续路径跟踪 → 已知地图规划”推进。跨平台方面，可先在现有静态组件/协议测试之外补代表性的真实浏览器烟测，再扩大实机矩阵；已有 CI 中的 Windows/macOS Rust 构建不等价于完整玩家流程受支持。

暂缓把多人 Arena、账号/排行榜、第三方代码托管、3D 物理或完整轮胎模型作为近期主线。当前原生玩家代码仍是本人可信代码；依赖白名单与 `-I` 进程不是敌对代码的 OS 沙箱。若未来推进 Arena，必须先完成服务端权威、执行隔离/配额和公平复现证据。独立静态网页分发同样需要解决浏览器侧持久化和启动依赖，当前 browser 模式仍依赖本地资源/工作区启动器。
