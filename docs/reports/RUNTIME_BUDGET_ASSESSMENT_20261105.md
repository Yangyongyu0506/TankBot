# 原生与浏览器 Runtime 时限评估

日期：2026-11-05。状态：评估与候选方案，尚未通过新 profile 长测，未修改默认配置、协议、模块合同或失败规则。本文重新分析已有隔离验收记录，没有新跑性能基准。机器可读数据、来源摘要与统计计算见 [证据 JSON](runtime-budget-assessment-20261105.json)。

## 判断

20 ms 不是由 60 Hz 物理或 10 Hz 算法频率推导出的要求。对本机原生已测轻量算法，它有明显余量；对 Pyodide，它混合了算法与多层消息排队成本，已出现正常参考解因截止结束整局的情况。建议后续试测 **原生整批墙钟 30 ms、浏览器整批墙钟 50 ms**，通过验收再成为默认运行 profile。

这两个数字是保守候选值，不是测量证明的最优值。已有证据支持区分后端，不能证明 50 ms 足以覆盖长期尾部、其他机器或后台标签页。当前原生 20 ms 没有被证实不够；30 ms 是为未来接近声明预算的合法算法预留宿主余量。

另有历史 1070c6c9 记录：367 批、一次恰好 20 ms 的浮点边界误判；源码已改为绝对截止比较。它保存在 JSON 中，但不能把它算作当前实现的调度超载。C2 另一次实验在第 25 批截止，已完成的 24 批往返 p99 为 18 ms；21 ms 是故障被观察到的时间，不是完整计算的完成耗时。

上述事件率只描述各自中止前观察到的批次。不能相加作为当前生产超时率，也不能忽略失败记录只汇总成功运行。早期浏览器部分往返直方图包含响应解码成本及历史截止实现差异，因此“直方图中大于 20 ms 的点数”不等于明确记录的截止事件数。

Python 批内运行是 `runtime_python_ms`，包含 Runner 分发与模块适配等工作。C2 原生单模块 `update_ms` p99 为 1.314 ms，浏览器为 3 ms；C4 原生四模块各自 update p99 约 0.252、0.077、0.230、0.061 ms。**各模块的 p99 不能相加当作整批算法 p99**，应对同一批的 update 求和后再计算分位数。现有汇总及最多 32 条公开最近记录不足以重建全部批次的这一分布。

内部遥测是可伪造的墙钟观察值，不是可信 CPU 记账；浏览器时钟还存在毫秒量化。不能把 `0 ms` 当作零计算成本，也不能直接用两个 p99 相减得到通信开销 p99。应逐批计算对应阶段差值，并承认它还包含未分解的调度成本。

## 时限与模块预算分开

拟采用的 profile 字段是设计语义，尚未加入配置或 Schema：

| 参数 | native_local_v1 | browser_pyodide_v1 |
| --- | ---: | ---: |
| batch_wall_deadline_ms：整批往返截止 | 30 ms | 50 ms |
| module_declared_budget_cap_ms：每次激活的模块声明预算总上限 | 20 ms | 20 ms |
| 物理频率 / 常用算法频率 | 60 Hz / 10 Hz | 60 Hz / 10 Hz |
| 固定提交门 | activation + 6 tick | activation + 6 tick |
| 超时处理 | 拒绝结果、终止 Worker，沿用课程失败规则 | 同左 |

候选估算使用 `ceil_to_10ms(max(20 + H, 2 × R99 + 10))`：取原生宿主预留 H=10 ms、浏览器预留 H=30 ms，R99 分别约 4.5 和 18 ms，得到 30 和 50 ms。倍数和预留量属于工程假设，用于生成试测候选，不是统计置信保证。原生 20/30 ms、浏览器 30/40/50 ms 均应参与对照。

现有 `runtime.batch_budget_ms` 同时用于模块声明准入与整批看门狗。直接把它改成 50 会连带提高模块声明总预算，不能用这一行修改实现上述设计。落实时须拆分配置并同步原生 Supervisor、BrowserSupervisor、iframe 看门狗、准入校验、公开 profile、Schema、诊断与文档。

20 ms 声明上限目前只是模块图准入约束；内部 update 遥测不能强制执行它。整批墙钟放宽后，实际算法也可能占用新增余量，不能声称仍拥有独立的 20 ms 算法硬限制。若未来 Arena 需要可信 CPU 配额，应另做 OS 级记账/隔离，不能依靠玩家可修改的遥测。

整批计时应统一从 Authority 开始编码请求，到 Authority 完成接收/解码响应；输入适配、update、输出构建、编码、IPC/跨 Worker 排队均计入。响应的权限与语义校验仍须在固定提交门前完成。iframe 本地看门狗用于终止失控 Worker，Authority 的同源单调时钟负责最终到期判定，不能仅依据 iframe 的较短桥接耗时。实现前需统一当前两后端在解码前后检查的口径，并测试解码跨越截止的情况。

50 ms 不增加控制器的仿真延迟：结果仍在第 6 tick 生效。6/60=100 ms 是名义仿真间隔，宿主追赶 tick 时不保证有完整 100 ms 现实时间；结果必须同时满足墙钟截止和固定提交门。不得为等待 Python 阻塞物理、移动提交门或扩大玩家 dt。不能用收到后的提交等待时间充当额外算法预算。

profile 在尝试开始前由可信宿主按后端选择并冻结，记录 ID、版本和完整参数，不按玩家代码的即时耗时自动扩容。标签页后台挂起或系统休眠时，沿用明确的暂停/失败策略，不能承诺任何有限墙钟时限消除这类影响。未来竞技环境须统一后端与运行条件，不能直接用本机教学 profile 宣称公平。

## 确认默认值需要的基准

1. 固定源码、依赖、种子、消息规模、配置与构建摘要，覆盖空 update、C2 KF、C3 EKF、四模块路径追踪，以及受控的接近声明预算工作负载。两后端分别记录浏览器/解释器版本、机器、前台状态与负载。冷启动、第一次激活和稳态分开报告，不能通过删首批隐藏正式运行会遇到的失败。
2. 先在隔离测试配置中用最高 80 ms 诊断看门狗观察尾部，保留固定提交门与真实页面调度；错过提交门和仍被终止的批次都记为截断/失败，不能当成完成耗时。授权输入回放可补测计算尾部，但其调度分布不能代替真实闭环。
3. 每个后端、主要工作负载和负载条件至少收集 10,000 批，跨多次尝试。流式保存逐批数据，不能只依赖当前 512 批滑动窗口和 32 条最近记录。报告 p50/p95/p99/p99.9、最大值、各阶段耗时、墙钟超时率、提交门错过率、完整尝试失败率；所有失败均保留，声明排除的非算法故障原因。
4. 在真实看门狗下分别运行候选时限，不只对同一份直方图改阈值。延迟会受终止、负载和调度变化影响；扩大时限也不能证明原本截止的那批会成功。验证死循环终止、恰好到期/刚超限、迟到不提交、重复响应、解码跨界、多模块满预算、宿主追赶和受控测试模式。
5. 选择达到课程完整尝试可靠性目标的最小时限；建议目标为正常前台运行中，由 Runtime 截止造成的完整尝试失败率低于 1%。若候选都无法达到，应检查排队/Host 追赶/验证开销，而不是无限放大看门狗。

10,000 批只是初步比较的样本门槛，不能直接证明上述可靠性目标。40 批零超时，在独立同分布假设下，单侧 95% 超时率上界仍约 7.22%；400 批零超时也约为 0.746%。所以现有零失败记录不足以宣称稳定。

对 120 秒、10 Hz、约 1,200 批的一局，若假设各批独立同分布，要达到 99% 整局不超时，单批概率需满足 `p <= 1 - 0.99^(1/1200)`，约 8.38×10^-6。单批 1% 超时率对应整局几乎必然超时；p99 不能直接作为硬截止线。若按更保守的单批 8×10^-6 目标，以零事件证明其单侧 95% 上界约需 374,466 批。现实调度故障可能聚集，仍须直接统计完整尝试并覆盖多次会话，不能只使用独立模型。

## 本轮结果

完成保存证据重分析和候选 profile 设计；未新跑原生或浏览器长测，未证明候选时限的实际改善幅度。现阶段可进入运行 profile 的实现和基准验证，不能把候选 30/50 ms 标为已验收默认值。此方案遵守 [ADR-0010](../adr/0010-simulation-scheduling.md) 的固定 tick 与定点提交原则；实现参数拆分及 profile 选择时再同步对应规范和决策记录。
